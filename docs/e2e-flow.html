End-to-end flow

The big picture

There is no backend server. The React app is a set of static files, and the browser talks directly to two Firebase services.

AWS Amplify

Hosts the built static files (index.html, JS, CSS) behind nezkos-garage.com. It only ever serves files.

React app (browser)

Runs everything: routing, screens, validation, photo resizing. Built with Vite, React Router and TanStack Query.

Firebase Auth

Handles Google sign-in and remembers who is signed in. Gives the app a user id (uid) and a token.

Cloud Firestore

The database. One collection, vehicles. Each request carries the user's token so Firestore knows who is asking.

The page-load journey

Follow one visit, in order. The same steps cover a first visit and a returning, already-signed-in visit; the difference is what step 3 finds.

  1. The browser fetches the app

    index.html → src/main.tsx

    The browser requests the site. Amplify returns index.html, which is nearly empty: a <div id="root"> and one script tag. The script is the built JavaScript bundle, and the page's CSS and the Google Fonts stylesheet load alongside it. Nothing is drawn yet.

    Network: static files only

  2. React boots and wraps the app in providers

    src/main.tsx → src/App.tsx

    main.tsx creates a TanStack QueryClient (the cache for server data) and renders <QueryClientProvider> around <App>, plus the Query Devtools panel (development builds only by default). App then nests <AuthProvider> and <BrowserRouter>, and renders <AppRoutes>.

    Importing lib/firebase.ts runs once at this point: it initializes the Firebase app, creates the Firestore instance (with ignoreUndefinedProperties on), and creates the Auth instance and the Google provider.

    Network: none

  3. Firebase restores the session

    src/context/AuthProvider.tsx

    AuthProvider starts with user = null and loading = true. In a useEffect it subscribes with onAuthStateChanged(auth, callback). Firebase looks in the browser's IndexedDB for a saved session. If one exists it quietly reloads that user (and may refresh the token in the background); if not, the user is null. Either way the callback fires once, the provider calls setUser(...) and setLoading(false), and everything below re-renders. The subscription stays open, so signing in or out later triggers the same callback.

    This is why the app has to wait: until that first callback, it does not know whether the visitor is signed in.

    Network: possible token refresh, no Firestore

  4. The router picks a page

    src/components/routing/AppRoutes.tsx · src/components/routing/RouteGuards.tsx · src/components/layout/AppLayout.tsx

    AppLayout wraps every route. It always draws the sticky Header and an <Outlet /> where the matched page goes. Inside it, two guard components decide what the visitor may see. While loading is true both show Loading... instead of guessing, so there is no flash of the wrong page.

    URLStill loadingSigned outSigned in
    / (RedirectIfAuthed)"Loading..."Landing pageRedirect to /vehicles
    /vehicles (RequireAuth)"Loading..."Redirect to /Vehicles page
    anything elseRedirect to /, then the row above applies

    The header also depends on auth: signed out it shows "How it works" (on the landing page only) and "Sign in"; signed in it shows the greeting and "Sign out".

    Network: none

  5. Signed out: the landing page

    src/pages/LandingPage.tsx · src/Constants.ts

    A signed-out visitor sees the hero, the "how it works" steps and a closing prompt. All of the text comes from Constants.ts. Both "Sign in with Google" buttons call signIn from useAuth(). No database is touched, so this whole path makes no Firestore requests. Sign-in is covered in its own section.

    Network: none beyond step 1

  6. Signed in: the vehicles page asks for data

    src/pages/VehiclesPage.tsx → components/vehicles/VehicleList.tsx → hooks/useVehicles.ts

    VehiclesPage reads the user from useAuth() and renders the title, the Add Vehicle button, and <VehicleList uid=...>. The list calls useVehicles(uid), which is a TanStack useQuery with the key ["vehicles", uid]. The cache has nothing under that key yet, so it runs the query function and the list shows "Loading vehicles..." meanwhile.

    The query function, getAllVehicles(uid) in api/vehicles.ts, is where the app finally talks to Firestore:

    query(
  collection(db, "vehicles"),
  where("owners", "array-contains", uid)   // only vehicles this user owns
)
getDocs(...)                                 // one request, returns every match

    The Firestore SDK opens a connection to Google's servers and attaches the signed-in user's Firebase token to the request. Firestore checks that token against its security rules, then returns every vehicles document whose owners array contains this uid. The function maps each document to { id, ...data }, giving a Vehicle[].

    Network: one Firestore query

  7. The data becomes components

    VehicleList.tsx → VehicleCard.tsx → MaintenanceSection.tsx

    When the query settles, VehicleList shows one of four things:

    • Loading: "Loading vehicles..."
    • Error: an alert with the Firestore message (after TanStack's default 3 automatic retries)
    • Empty: "No vehicles yet."
    • Data: a grid with one <VehicleCard> per vehicle

    Each card renders the photo, name, year/make/model, a details grid (color, mileage, plus trim, VIN and plate when present), and a <MaintenanceSection>. That section never makes its own request: the maintenance records are already inside the vehicle document that was just fetched. It sorts them newest-first in the browser, shows the latest one as "Last: Oil change on ...", and opens the full list in a modal.

    Network: none, uses the cached result

Signing in with Google

The app never sees a password. It asks Firebase to run a Google sign-in popup and then reacts when Firebase says the user changed.

The pieces that make it work

  • signIn is () => signInWithPopup(auth, googleProvider), defined in AuthProvider and exposed through useAuth(). The popup runs on Firebase's own domain and Google's pages.
  • The result is not returned to the button. The app does not wait on that promise to update the screen. It relies on the onAuthStateChanged listener from step 3 of the journey, which fires for sign-in, sign-out and session restore alike. One code path handles all three.
  • Sign out is signOut(auth). The same listener fires with null, RequireAuth sends the visitor to /, and the header returns to its signed-out buttons.
  • Staying signed in: Firebase keeps the session in the browser's IndexedDB, so a refresh or return visit restores the user without showing Google again.
  • Why Firestore trusts the request: once signed in, every Firestore call carries the Firebase token. The rules (kept in the Firebase console, not in this repo) can read the user's uid from it.

What's stored in Firestore

One collection, vehicles. Each document is a whole vehicle, including its service history and its photo.

vehicles/{vehicleId}
{
  name: "Soupra",             year: 2026,
  make: "Toyota",             model: "Supra",
  color: "Absolute Zero",     mileage: 7800,
  trim?, vin?, licensePlate?,                // optional
  photo?: "data:image/jpeg;base64,...",      // resized in the browser, stored inline
  owners: ["<uid>", ...],                    // who may see it; the query filters on this
  maintenance: [                             // embedded array, no sub-collection
    { id, type: "oil_change", date: "2026-07-13", mileage?, cost?, details? }
  ],
  wishlist: [                                // embedded array, like maintenance
    { id, name, link, price,                 // price = what you want to pay
      currentPrice?, lastCheckedAt?, priceError? }  // written only by the price checker
  ],
  createdAt, updatedAt                       // server timestamps
}
  • Ownership: owners is an array of user ids. The app's query is owners array-contains uid, so each person only gets their own vehicles back.
  • Maintenance is embedded: that is why the card needs no second request, and why adding a service is a single update to the vehicle document.
  • Dates are strings: entries use "YYYY-MM-DD", which sort correctly as text. That is how the list gets sorted newest-first with a plain string compare.
  • Photos live in the document: lib/image.ts scales the chosen image to at most 800px, re-encodes it as a JPEG and rejects anything over about 600,000 characters. A Firestore document is limited to 1 MB and the photo shares that with the service records. There is no separate file storage.
  • Types: the TypeScript shapes (Vehicle, MaintenanceEntry, the service-type list and labels) are in src/types/vehicle.ts. Entry ids come from newId() in lib/id.ts.

The data layer

Components never call Firestore directly. Each request passes down the same four layers, and the answer comes back up.

ComponentVehicleList, VehicleForm, MaintenanceSection… Ask for data or trigger a change and render the result.
Hookhooks/useVehicles.ts: useVehicles(uid) for reading, useCreateVehicle, useUpdateVehicle, useDeleteVehicle, useSetVehiclePhoto and the three maintenance hooks for writing. Wraps TanStack Query.
API functionapi/vehicles.ts: plain async functions such as getAllVehicles and addNewVehicle. The only place Firestore calls are written.
Firebase SDKlib/firebase.ts creates the Firestore and Auth instances. The SDK adds the user's token and talks to Firebase's servers.

How TanStack Query behaves here

  • Cache key: ["vehicles", uid]. Everything about a user's vehicles sits under that one key, so two components asking for it share one request.
  • Settings: the app uses the library defaults (new QueryClient() with no options): data counts as stale immediately, refetches when the window regains focus or a component remounts, and retries a failed request 3 times.
  • Reads use getDocs, not a live listener, so the screen updates on a refetch, not the instant something changes elsewhere.

What happens when someone saves

Every change follows the same loop: write to Firestore, then tell the cache its data is out of date so it fetches the fresh list.

  1. Form validation, in the browser

    VehicleForm and MaintenanceForm check the fields on submit and show an inline error. The six required vehicle fields are marked with an asterisk. Nothing is sent until the checks pass.

  2. A mutation hook calls the API function

    For example, useCreateVehicle(uid).mutate(input) calls addNewVehicle, which does addDoc on the vehicles collection with the form fields plus owners: [uid], an empty maintenance array and server timestamps. While it runs, the button shows "Saving...".

  3. The cache is invalidated and refetched

    All the mutation hooks share one helper that, on success, calls invalidateQueries({ queryKey: ["vehicles", uid] }). TanStack Query immediately re-runs getAllVehicles for the list on screen, and the new card appears. The modal then closes.

ActionFirestore operation
Add vehicleaddDoc on vehicles
Edit vehicle detailsupdateDoc; cleared optional fields use deleteField() so they are removed, not saved as undefined
Add / change / remove photoupdateDoc on the photo field
Delete vehicledeleteDoc (the maintenance records go with it, since they are inside the document)
Add a service recordupdateDoc with arrayUnion of a new entry with a generated id
Add a wish list itemupdateDoc with arrayUnion of a new item with a generated id
Edit / delete a wish list itemrunTransaction, like service records. On edit, the checker's fields (currentPrice, lastCheckedAt, priceError) are kept unless the link changed, because an old price no longer applies to a new link.
Edit / delete a service recordrunTransaction: read the document, change the array in memory, write it back, so two quick edits cannot overwrite each other

The daily price checker

The one piece that runs without anyone opening the app. A small AWS Lambda visits every wish list link once a day and writes what it finds back onto the item.

EventBridge Scheduler

Invokes the Lambda once a day. Nothing in the app triggers it.

Lambda price-checker

Node.js, in functions/price-checker/. Not deployed by Amplify: it is zipped and uploaded by hand in the Lambda console.

Parameter Store

Holds the Firebase service account JSON (SecureString). Read once per container; never committed to the repo.

Cloud Firestore

Read and written through the Admin SDK, which bypasses security rules. That is why the Lambda's AWS role is limited to Parameter Store read and logs.

One run, step by step

  1. The schedule fires

    EventBridge Scheduler → handler in index.mjs

    The Lambda loads the service account from Parameter Store, starts the Admin SDK and opens Firestore.

  2. It fetches each item's page

    checkItem

    For every vehicle, every wish list item that has a link is fetched (10 second timeout, a browser-like user agent). A non-2xx response is recorded as "HTTP <status>", for example "HTTP 403".

    Network: one request per wish list item

  3. It reads the price from the page

    extractPrice, findPrice

    The page's application/ld+json blocks are parsed and searched (including @graph and arrays) for offers.price or lowPrice. Malformed blocks are skipped. If nothing usable is found the item gets priceError: "no price found". Only sites that publish structured data work.

  4. It writes the result back safely

    Fetching is slow, so the user may have edited the vehicle in the meantime. The Lambda re-reads the document inside a transaction and merges results into the current wishlist array by item id, so those edits are not overwritten. A success sets currentPrice and lastCheckedAt and clears any old priceError; a failure sets priceError and lastCheckedAt.

    Network: one Firestore transaction per vehicle

  5. The app shows it

    WishListItemCard, lib/priceError.ts

    Nothing is pushed to the browser. The next time the vehicles query runs (page load, tab focus or after a change), the wish list reads the updated fields. See the table below.

What the wish list shows

Item's dataOn the card
currentPrice < priceGreen price drop notice with the amount saved and percent off.
currentPrice ≥ priceBoth prices are shown, no notice.
priceError is HTTP 401, 403 or 429Red notice: this website blocks automated price checks, so the price can't be tracked automatically. statusFromPriceError reads the number out of the saved text; isPriceCheckBlocked decides.
Any other priceError (404, 500, "no price found")Nothing shown yet. The old currentPrice, if any, stays.
No check has run yetOnly the price you want to pay is shown.
Known limits. Many retailers block bots or don't publish JSON-LD, so some items will show the red notice or stay unchecked. Links are fetched as given, so a hardened version would restrict which hosts the Lambda may call. Items are checked one after another, and there is no alert if a run fails; the only trace is the CloudWatch log line with the number of items checked.

How it gets to the browser

The path from a commit to the page someone loads.

  1. Push to main

    Amplify watches the repo and starts a build on every push.

  2. Build

    npm run build, which type-checks with tsc -b and then bundles with Vite into dist. A failed build leaves the live site on the last good version.

  3. Serve

    Amplify serves dist at nezkos-garage.com (domain managed in Route 53).

Deep links need a rewrite rule. The app has real URLs now (/vehicles), but only index.html exists as a file. For a refresh or a pasted link to work, Amplify needs a rewrite that sends unknown paths to /index.html with a 200 status. This is an Amplify console setting.

Good to know

  • Access control lives in Firestore rules, not in the React code. The owners array-contains uid filter selects the right documents, but the rules are what stop someone from asking for another user's. Those rules are configured in the Firebase console and are not in this repo, so this document does not describe their contents.
  • Whole vehicles are fetched every time. Because photos and service history are inside each document, the list request grows with them. The 1 MB document limit is the ceiling, which is why photos are shrunk before saving.
  • Not live. Changes made on another device show up on the next refetch (focus the tab, or make a change), not instantly.
  • A naming quirk: in lib/firebase.ts the Firestore instance is exported as vehicleCollection, but it is the whole database object, which api/vehicles.ts then passes to collection(...) and doc(...).
  • Firebase config in the code is not a secret. The values in lib/firebase.ts identify the project to Firebase. What protects the data is sign-in plus the Firestore rules.
