Overview

There are two halves. The user-facing app is a static React app on AWS Amplify that talks straight to Firebase, with no backend server. The scheduled job is an AWS Lambda that checks wish list prices once a day. Firestore is where the two meet.

Code layout

The front end is organized by layer. Each layer only talks to the one below it, so UI components never call Firebase directly.

ComponentsPages and feature UI, grouped by area: components/vehicles, wishlist, layout, routing, common. Route pages live in pages/. User-facing text lives in Constants.ts.
Hookshooks/useVehicles.ts and hooks/useWishlist.ts wrap every read and write in TanStack Query. Mutations invalidate the ["vehicles", uid] cache so the UI refreshes on its own. useAuth exposes the auth context.
ContextAuthProvider subscribes to onAuthStateChanged and provides user, loading, signIn, signOut. Route guards use it to decide which pages render.
Servicesservices/vehicles.ts and services/wishlist.ts hold every Firestore call. Adds use arrayUnion; edits and deletes go through editVehicleList, a transaction that does read-modify-write so concurrent edits aren't lost.
Lib, utils and typeslib/firebase.ts (SDK setup), utils/image.ts (resize photos under the 1 MB document limit), utils/priceError.ts, utils/format.ts, utils/id.ts. types/vehicle.ts is the single source of truth for the data model.

Tests sit next to the code as *.test.ts(x) and run with Vitest and Testing Library (npm test). The Lambda's price parsing is tested in functions/price-checker/price.test.mjs.

Key flows

The two paths data takes through the system. The end-to-end flow covers page load and sign-in in more detail.

A user logs maintenance

  1. Sign in

    Google sign-in through Firebase Auth gives the browser an ID token.

  2. Submit

    The form calls a mutation hook, which calls addMaintenanceEntry in services/vehicles.ts.

  3. Rules check

    Firestore checks the token against the rules: signed in, UID in owners, fields valid.

  4. Refresh

    The write succeeds, TanStack Query invalidates the cache, and the list refetches.

The nightly price check

  1. Schedule fires

    EventBridge Scheduler invokes the Lambda once a day.

  2. Load credentials

    The Lambda reads the service account from Parameter Store and starts the Admin SDK (cached per container).

  3. Fetch prices

    Each wish list link is fetched with a 10 second timeout and the price is read from JSON-LD.

  4. Merge safely

    Results are written in a transaction that merges by item ID, so edits made during the run aren't overwritten.

Security model

With no backend, the security boundary is the Firestore rules, not the React code. Anything in the browser can be bypassed, so the browser is never trusted.

ConcernHow it's handled
AuthenticationGoogle sign-in through Firebase Auth. The app never sees a password; Firestore requests carry the Firebase ID token.
AuthorizationFirestore rules: every request must be signed in, and a vehicle can only be read or changed by users in its owners array. Route guards are only for user experience.
Data validationRules validate required fields, types and limits on create and update, and prevent changing owners after creation. Forms validate too, for a better experience.
QueryingRules aren't filters. The owners array-contains uid query is what lets list requests pass the rules.
Firebase web configThe values in lib/firebase.ts identify the project and aren't secrets. Every browser downloads them.
Privileged accessOnly the Lambda uses the Admin SDK, which bypasses rules. Its service account is a SecureString in Parameter Store, read by name from SA_PARAM, and never committed.
TransportHTTPS everywhere, with an Amplify-managed certificate from AWS Certificate Manager.
Hardening next. Keep the rules in the repo with emulator tests; restrict the API key to the site's domains and add App Check; limit the Lambda to https: links and block private IP ranges (SSRF); narrow the service account's role or replace the key with Workload Identity Federation.

Scaling

Sized for a household. The managed pieces scale on their own; the limits are in the app's own choices.

Scales without changes

  • Static hosting on Amplify's CDN
  • Firebase Auth
  • Firestore capacity, with random document IDs avoiding write hotspots

Would need to change

  • Page loads: whole vehicles, photos included, come back on every list fetch. Move photos to object storage and paginate history in a subcollection.
  • Refetching: default TanStack settings refetch on focus and after every change. Tune staleTime or use real-time listeners.
  • Price checker: one run reads every vehicle, checks each vehicle's links in parallel and moves through the vehicles one at a time, all within Lambda's 15 minute limit. There is no dead-letter queue or alarm today.
